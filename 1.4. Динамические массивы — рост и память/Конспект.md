# 1.4. Массивы. Часть 2

## Самая короткая версия

Динамический массив умеет расти, хотя память под обычный массив выделяется цельным блоком фиксированной ёмкости.

Когда свободное место заканчивается, структура:

1. выделяет новый, более крупный блок;
2. копирует туда старые элементы;
3. добавляет новый элемент;
4. перестаёт использовать старый блок.

Python `list` и JavaScript `Array` делают такую работу автоматически. Именно поэтому разработчик может вызывать `append()` или `push()` и не указывать окончательный размер заранее.

## Зачем нужны size и capacity

```text
size = 4
capacity = 8

[A] [B] [C] [D] [_] [_] [_] [_]
```

Пока `size < capacity`, новый элемент можно положить в свободную ячейку.

```text
size = 8
capacity = 8

[A] [B] [C] [D] [E] [F] [G] [H]
```

Теперь свободных ячеек нет. Продолжить запись в соседнюю память нельзя: она может принадлежать другой части программы. Нужен новый блок.

## Почему нельзя просто добавить один байт справа

Массив должен занимать непрерывную область памяти. Пространство непосредственно после него может быть занято. Поэтому система не обязана иметь возможность расширить существующий блок на месте.

Это похоже на заполненный ряд мест в кинотеатре: если группе нужно больше соседних мест, нельзя приказать людям в следующем ряду исчезнуть. Приходится пересадить всю группу в более длинный свободный ряд.

## Упрощённая реализация динамического массива на Python

Это учебная реализация, а не замена встроенному `list`:

```python
import ctypes


class DynamicArray:
    def __init__(self):
        self.size = 0
        self.capacity = 1
        self._data = self._make_array(self.capacity)

    def __len__(self):
        return self.size

    def __getitem__(self, index):
        if not 0 <= index < self.size:
            raise IndexError("index out of range")
        return self._data[index]

    def append(self, value):
        if self.size == self.capacity:
            self._resize(self.capacity * 2)

        self._data[self.size] = value
        self.size += 1

    def _resize(self, new_capacity):
        new_data = self._make_array(new_capacity)

        for index in range(self.size):
            new_data[index] = self._data[index]

        self._data = new_data
        self.capacity = new_capacity

    @staticmethod
    def _make_array(capacity):
        return (capacity * ctypes.py_object)()
```

`ctypes.py_object` означает, что ячейки хранят ссылки на Python-объекты. Реальный CPython устроен сложнее и использует собственную стратегию роста; удвоение здесь выбрано для простого объяснения идеи.

## Почему append иногда O(n)

Обычная вставка в свободную ячейку:

```text
[A] [B] [C] [_]
            ^ записали D
```

занимает `O(1)`.

Но при заполненной ёмкости нужно скопировать все `n` старых ссылок:

```text
старый: [A] [B] [C] [D]

новый:  [A] [B] [C] [D] [E] [_] [_] [_]
```

Такая отдельная вставка занимает `O(n)`.

При этом для `append` указывают **амортизированную сложность `O(1)`**. Это не ошибка.

## Что такое амортизированная сложность

Амортизированный анализ рассматривает длинную последовательность операций и распределяет редкие дорогие действия между множеством дешёвых.

Пусть ёмкость удваивается:

```text
capacity: 1 -> 2 -> 4 -> 8 -> 16
копий:         1    2    4    8
```

Чтобы добавить 16 элементов, мы выполним 16 обычных записей и скопируем примерно `1 + 2 + 4 + 8 = 15` старых элементов.

Общий объём работы остаётся порядка `n`, а операций добавления тоже `n`. В среднем на одну операцию приходится константный объём работы:

```text
O(n) / n = O(1)
```

Это и называется амортизированным `O(1)`.

Важно: конкретный вызов `append` иногда всё равно может быть дорогим. Амортизированная оценка относится к последовательности вызовов.

## Почему рост на фиксированное число хуже

Представим, что ёмкость каждый раз увеличивается только на 10:

```text
10 -> 20 -> 30 -> 40 -> ...
```

По мере роста придётся всё чаще копировать всё более длинный массив. Суммарное число копирований будет расти квадратично.

При умножении ёмкости на некоторый коэффициент расширения происходят гораздо реже, поэтому суммарная стоимость последовательных добавлений остаётся линейной.

Реальные реализации не обязаны удваивать ёмкость ровно в два раза. Важна идея геометрического роста, а конкретный коэффициент — инженерный компромисс между скоростью и лишней памятью.

## Почему аллокации считают дорогими

Аллокация — запрос нового блока памяти. Она требует работы менеджера памяти. При расширении массива к этому добавляется копирование элементов.

Поэтому, когда приблизительный объём известен заранее, во многих языках полезно заранее зарезервировать ёмкость. В обычном Python `list` прямого публичного `reserve()` нет, и чаще всего достаточно полагаться на встроенную реализацию.

Не следует вручную «оптимизировать аллокации» без измерений. Основной практический вывод для Python-разработчика проще:

- `append` подходит для постепенного накопления данных;
- многократное создание копий большого списка может быть дорого;
- `items = items + [value]` в цикле хуже обычного `items.append(value)`, потому что `+` создаёт новый список.

Плохо:

```python
result = []

for value in source:
    result = result + [value]
```

Хорошо:

```python
result = []

for value in source:
    result.append(value)
```

## Почему массив не уменьшают при заполнении ровно наполовину

Допустим, структура:

- увеличивает ёмкость вдвое при полном заполнении;
- уменьшает ёмкость вдвое, как только заполнена только половина.

Тогда добавление и удаление около границы могут вызвать постоянные пересоздания:

```text
добавили -> расширили -> удалили -> уменьшили -> добавили -> расширили...
```

Это называется «дребезгом» или thrashing.

Поэтому в учебной стратегии:

- расширяем при `size == capacity`;
- уменьшаем, когда `size <= capacity / 4`;
- новую ёмкость делаем примерно вдвое меньше.

Между границами остаётся запас, и дорогие операции не повторяются на каждом шаге.

Конкретные реализации Python и JavaScript могут использовать другие правила. Здесь важен общий принцип гистерезиса: порог уменьшения должен находиться заметно ниже порога увеличения.

## Задача: слияние двух отсортированных массивов

Даны:

```python
first = [1, 3, 8, 10]
second = [1, 3, 7, 9, 11]
```

Нужно получить один отсортированный список:

```python
[1, 1, 3, 3, 7, 8, 9, 10, 11]
```

Используем два индекса:

```python
def merge_sorted(first, second):
    merged = []
    first_index = 0
    second_index = 0

    while first_index < len(first) and second_index < len(second):
        if first[first_index] <= second[second_index]:
            merged.append(first[first_index])
            first_index += 1
        else:
            merged.append(second[second_index])
            second_index += 1

    merged.extend(first[first_index:])
    merged.extend(second[second_index:])

    return merged
```

Почему результат остаётся отсортированным:

1. Смотрим на самые маленькие ещё не обработанные элементы обоих списков.
2. Выбираем меньший.
3. Передвигаем индекс только в том списке, откуда взяли элемент.
4. Когда один список закончился, остаток второго уже отсортирован и больше ранее выбранных элементов.

Сложность:

- время — `O(n + m)`;
- дополнительная память для результата — `O(n + m)`.

Здесь `n` и `m` — длины двух списков.

## Почему не объединить и не отсортировать

Так тоже получится корректный результат:

```python
merged = sorted(first + second)
```

Но общий алгоритм сортировки потребует примерно `O((n + m) log(n + m))`. Он не использует полезную информацию о том, что оба входных списка уже отсортированы.

Линейное слияние `O(n + m)` быстрее по порядку роста и является важной частью сортировки слиянием.

В реальном приложении короткая запись через `sorted` иногда вполне разумна: библиотечный код хорошо оптимизирован, а простота важна. Выбор делают с учётом объёма данных, требований и измерений.

## JavaScript-версия слияния

```javascript
function mergeSorted(first, second) {
  const merged = [];
  let firstIndex = 0;
  let secondIndex = 0;

  while (firstIndex < first.length && secondIndex < second.length) {
    if (first[firstIndex] <= second[secondIndex]) {
      merged.push(first[firstIndex]);
      firstIndex += 1;
    } else {
      merged.push(second[secondIndex]);
      secondIndex += 1;
    }
  }

  return merged
    .concat(first.slice(firstIndex))
    .concat(second.slice(secondIndex));
}
```

Логика не изменилась: язык поменял только синтаксис.

## Где слияние применяется на практике

- объединение отсортированных результатов из двух источников;
- обработка событий из нескольких хронологических потоков;
- объединение страниц или файлов, уже отсортированных по времени;
- сортировка слиянием;
- сравнение двух версий отсортированных данных;
- объединение результатов нескольких серверов.

## Что важно запомнить

1. Динамический массив растёт путём выделения нового блока и копирования.
2. Отдельный `append` иногда стоит `O(n)`, но последовательность добавлений — амортизированно `O(1)` на операцию.
3. Геометрический рост ёмкости нужен, чтобы расширения происходили редко.
4. Уменьшение на другом пороге защищает от постоянного расширения и сжатия.
5. Два отсортированных массива можно слить за `O(n + m)` с помощью двух индексов.
